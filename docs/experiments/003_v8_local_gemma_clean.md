## Failure Analysis

### Gravity (0/17, 0%)
Model is learning the d = 0.5·g·t² formula but estimating g incorrectly from in-context examples.
Generates plausible numeric answers that are consistently off. The post-hoc reasoning traces
provide the correct answer but vary in how they express the g derivation — model hasn't
converged on the right g extraction strategy.

### Unit Conversion (1/17, 5.9%)
Similar issue: model identifies the transformation type (e.g. "subtract 0.18") but applies
the wrong constant in most cases. One success suggests the pattern is learnable.

### Bit Manipulation (1/17, 5.9%)
Model identifies operation type (rotation, XOR, etc.) correctly in reasoning but applies it
incorrectly to the specific input. Short one-sentence reasoning doesn't encode the exact
operation precisely enough.

### Symbol Transform (0/17, 0%) — notable regression
Parse rate dropped from 58.8% → 76.5% (improvement), but accuracy remains 0%.
**Key issue:** 2 of the incorrect examples show the repair-sourced reasoning leaking into
inference: `"The correct symbol sequence is provided for this post-hoc training trace, so I
copy it exactly."` The 355 repair rows in training used a fixed generic reasoning string, and
the model learned to emit it. This reasoning provides no real signal for solving the puzzle.
Recommend: exclude deterministic_symbol_copy_repair_v8 rows from the next training run,
or replace their reasoning with task-specific strings before training.

### Cipher Text (6/17, 35.3%) — biggest improvement (+17.7%)
Model is genuinely learning substitution cipher patterns. Failures are mostly near-misses
(correct structure, one word wrong). Strong signal that longer post-hoc reasoning traces
help here vs haiku's shorter traces.

## Key Observations

1. **Parse improved significantly** (86.3% → 96.1%) — V8 data produces cleaner output format
2. **Cipher_text breakthrough** (+17.7%) — biggest single-task gain; longer reasoning helps
3. **Repair row leakage** — symbol_transform repair reasoning strings bleed into inference
4. **Gravity/numerical tasks remain at 0%** — short reasoning traces insufficient for exact numeric reasoning; likely needs longer max_new or multi-step chain-of-thought
5. **Val loss 0.344 vs haiku baseline 0.477** — V8 data is a better training signal despite fewer rows

## Next Steps to Consider

- Exclude or re-reason symbol_transform repair rows before next training run
- Try max_new=400-500 for gravity/unit_conversion at eval time
- Consider longer reasoning traces for numerical tasks in next data generation pass
